### A 서버와 통합

- 기존 업로드 흐름을 보존하면서 화면 렌더링을 `src/views/`로 한 번만 분리합니다. 분리 커밋이 공유된 뒤 D가 해당 경로를 맡습니다
- `courseId`, `userId`, `materialId`, `conceptId`, `questionId`, `attemptId`와 공통 저장소 접근 방식을 정합니다. B–E는 자체 저장 파일이나 별도 DB를 만들지 않습니다
- 사용자 식별·과목 접근 확인은 공통 계층에서 맡고, 다른 모듈에는 확인된 사용자·과목을 전달합니다. 요청 본문의 임의 사용자 ID만 믿고 검수자를 판정하지 않습니다
- 각 모듈의 라우트·MCP 연결, 오류 응답, 의존성 추가, 실행 명령, 실제 배포 환경을 통합합니다
- 14:40부터 통합 장애 수정에 집중합니다. 모든 기능을 대신 구현하거나 다른 담당 파일을 임의로 고치지 않습니다

**완료 기준:** 새 환경에서 문서대로 서버가 켜지고, 기존 업로드가 유지되며, B–E 기능이 같은 데이터와 사용자·과목 기준으로 이어집니다. 공개 URL의 실제 접속·업로드·MCP 가능 여부를 E와 확인합니다.

### B 교안 처리

- PDF 형식·빈 파일·크기·과목당 파일 수를 검사하고, 텍스트가 없는 PDF와 처리 실패를 구분합니다
- 페이지 번호를 유지해 청크를 만들고, 파일 해시로 중복 처리를 막습니다. 실제 임베딩이 연결되면 청크와 함께 저장합니다
- A의 저장소 인터페이스를 사용하고 C에는 `materialId + page + text`가 있는 맥락을 제공합니다
- PRD의 50MB가 배포 환경에서 가능한지 A와 검증합니다. 시간 안에 20MB만 지원하면 화면·매뉴얼·검증표에 같은 제한을 표시하고 FR-01을 부분 구현으로 남깁니다
- 임베딩 미연결이나 실패를 성공으로 표시하지 않습니다. 텍스트 추출만 되는 경우도 별도 상태로 기록합니다

**완료 기준:** 샘플 PDF의 본문과 페이지를 MCP에서 다시 찾을 수 있고, 동일 파일·비PDF·빈 파일·텍스트 없는 PDF를 넣었을 때 저장·재처리 여부와 안내가 일치합니다.

### C MCP와 문항 검수

- 필수 도구 `get_course_context`, `submit_concepts`, `get_question_bank`, `submit_questions`, `get_review_batch`, `submit_reviews`를 작은 흐름부터 연결합니다
- B의 청크를 그대로 근거로 사용하고, 개념 요약 길이·근거 페이지·선수 관계, 문항 난이도·선택지·정답·1차 검수 4항목과 사유를 검사합니다
- 문항 생성은 사용자 AI가 담당합니다. 운영 서버에서 생성형 LLM을 새로 호출하지 않습니다
- 1차 통과·검증 완료·숨김 상태와 검수 이력을 관리합니다. 2차 통과 2건은 서로 다른 검수자여야 하며 같은 사용자의 반복 제출로 집계하지 않습니다
- D에는 해당 사용자에게 출제 가능한 문항만 제공합니다. 숨김·접근 불가 문항과 풀이 전 정답이 일반 문제 조회에 섞이지 않게 합니다

**완료 기준:** 실제 MCP 클라이언트에서 맥락 조회→개념·문항 제출이 되고, 잘못된 제출은 거절됩니다. 작성자 1명과 별도 검수자 2명의 테스트 사용자로 상태 변화를 재현합니다. 이 테스트 사용자들은 위 A–E 팀원 역할과 다른 개념입니다.

### D 학습 화면과 채점

- A가 분리한 화면 경로에서 업로드 상태·MCP 주소 안내·개념 스테이지 맵·플레이·결과 화면을 연결합니다
- 첫 스테이지 열림, 선수 스테이지 잠금, 5개 단위 유닛, 문항 부족·검수 필요·이용권 필요 상태를 구분해 보여 줍니다
- `src/study/`에서 객관식 채점·시도 기록·4/5 클리어·XP·별·다음 스테이지 해금을 처리합니다. E의 이용권 판정 결과를 사용하며 별도 결제 규칙을 만들지 않습니다
- 같은 답안 재전송·버튼 연타·새로고침으로 XP와 별이 중복 증가하지 않게 합니다
- ★1 전체 흐름을 먼저 완성합니다. ★2·★3·주관식 임베딩 채점·오답 재출제·숙련도 중 남은 부분은 검증표에 명시합니다

**완료 기준:** 실제 C의 문항 5개를 풀어 4개 정답이면 클리어와 다음 스테이지 열림, 3개면 재도전이 보입니다. 문항 부족과 오류 때도 화면이 멈추지 않습니다. 모바일 폭에서 업로드·선택지·결과를 사용할 수 있습니다.

### E 이용권과 검증 및 데모

- 첫 5개 무료·6번째부터 이용권 필요·중복 구매 방지·실패·만료 판정을 한 모듈로 제공합니다. D의 화면과 C의 MCP는 합의된 같은 정책을 사용합니다
- PRD가 허용한 테스트 결제 모의 버튼을 우선 사용할 수 있습니다. 모의 결제와 실제 토스 테스트 연동을 구분해 표시하고 실제 금전 결제는 넣지 않습니다
- 개인정보·비밀키·실제 수업자료 공유 문제가 없는 작은 샘플 PDF, 기대 청크·개념·문항, 테스트 사용자와 초기화 절차를 준비합니다
- 통합 직전부터 아래 검증표를 채우고, 결함은 해당 파일 소유자에게 입력·기대 결과·실제 결과·커밋을 묶어 전달합니다

**완료 기준:** 이용권 유무·성공·실패·중복·만료 사례가 재현되고, 처음 보는 팀원도 매뉴얼대로 대표 흐름을 실행할 수 있습니다. 3분 데모와 제출 항목을 준비합니다.

## 3 파일 충돌을 막는 규칙

1. **현재 `server.js`는 A 한 명만 수정합니다.** B–E는 새 모듈과 테스트를 만들고, 필요한 연결부를 PR 설명에 적습니다. D도 분리 전 `renderPage`를 직접 동시에 수정하지 않습니다
2. `package.json`·lockfile·공통 저장소·배포 설정은 A가 관리합니다. 새 패키지가 필요하면 이름·용도·버전을 A에게 먼저 전달합니다
3. 모듈별 상태는 A가 정한 저장소를 통해 읽고 씁니다. 기존 `uploads/metadata.json`이나 서로 다른 JSON 파일에 각자 규칙을 추가하지 않습니다
4. `README.md`·`CLAUDE.md`·`AGENTS.md`·`CONTRIBUTING.md`는 [협업 지침 PR #1](https://github.com/Snow0821/AltTab/pull/1)과 겹칩니다. 이 분업 문서에서는 수정하지 않으며, 이후 수정도 해당 PR 상태와 담당자 확인 후 한 사람이 맡습니다
5. 각자 최신 기준에서 작업 브랜치와 작은 Draft PR을 만듭니다. PR에 담당 경로·연결 요청·실행한 검증·미구현 부분을 적습니다
6. Mint 검토·병합 순서는 **A의 최소 골격 → B/C 데이터·MCP → D 학습 → E 이용권·통합 검증**을 기본으로 하되 독립 PR은 먼저 검토할 수 있습니다. 작업 담당자가 `main`에 직접 밀어 넣지 않습니다
7. 다른 담당 파일의 수정이 필요하면 원래 담당자에게 요청하거나 담당 이전을 PR에 기록합니다. 급하다는 이유로 여러 명이 공통 파일을 동시에 편집하지 않습니다

## 4 13시까지 합의할 계약

A가 `docs/api-contract.md` 초안을 한 곳에서 관리하고 B–E가 예시 요청·응답 한 개씩 확인합니다. 아래 경로·필드는 출발점이며, 이미 만들어 둔 구현이 있으면 함께 조정한 뒤 고정합니다.

| 연결 | 계약 초안 | 담당 연결 |
| --- | --- | --- |
| 기존 업로드 | `POST /upload`, multipart 필드 `pdf` 유지. 기존 화면 리다이렉트 동작을 깨지 않고 처리 상태를 추가 | A ↔ B ↔ D |
| 교안 맥락 | `get_course_context({courseId})` → `materials`, `chunks[{materialId,page,text}]`, 처리 상태. 준비 안 됨과 빈 결과 구분 | B → C |
| 개념·문항 | 개념 ID와 근거 페이지를 공통 키로 사용. `submit_questions`는 문항별 성공/거절 사유와 ID 반환 | C → D |
| 학습 시작 | 제안: `POST /api/stages/:stageId/attempts` → `attemptId`, 문제 5개, 진행 상태. 풀이 전 정답·해설 제외 | A ↔ C ↔ D |

- **무료 체험과 MCP 권한:** FR-02는 이용권 없는 MCP 사용을 막지만 FR-06은 첫 5개 스테이지를 무료로 제공합니다. 무료 구간에서 MCP로 직접 출제할 수 있게 할지, 준비된 문항만 체험하게 할지 13:00에 정하고 C·D·E가 같은 규칙을 씁니다
