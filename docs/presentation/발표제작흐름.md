# passfinder 발표 제작 흐름

이 문서는 팀의 발표 제작 순서와 담당 제안이다. [발표자료 제작 원칙](발표자료_제작원칙_공유용.md)을 따르고, 요구사항은 [단일 PRD](../../passfinder-prd.md)를 기준으로 한다. [서버·DB 구현 지시](../클로드_공통시험_구현지시.md)에 따라 구현과 확인을 진행한 뒤 발표 내용을 확정한다. UI 제작은 별도 담당자가 맡는다.

## 1. 발표에서 설명할 범위

발표의 중심은 **교안에서 만든 같은 문제를 학생들이 풀고, 결과를 비교하며 풀이를 참고하는 학습 경험**이다. 학생이 문제를 준비하고 혼자 답을 확인하는 과정을 줄이는 것이 목표다. 준비 시간 감소, 문항 품질, 지불 의향은 따로 확인한다.

| 대상 | 제작 기준 |
| --- | --- |
| 현재 제출 후보 | Express의 교안 기반 5문항 생성과 브라우저 저장 흐름을 먼저 배포 주소에서 확인한다 |
| 이번 핵심 구현 | 같은 시험과 같은 문항 버전을 공유하고, 서버에서 채점한 결과와 풀이를 함께 보는 기능이다. 구현·확인 전에는 완료로 표시하지 않는다 |
| 확정한 차별성 | 같은 문제를 푼 학생들의 결과를 비교하고 다른 풀이를 참고한다. AI 문제 생성만으로 차별성을 설명하지 않는다 |
| 현재 한계 | 기존 점수 화면은 공동시험 결과의 증거로 사용할 수 없다. 시험별 구분·서버 채점·저장을 확인해야 한다. Next.js에 관련 코드가 있어도 연결 완료로 설명하지 않는다 |
| 가격과 원가 | 월 구독인지 과목 이용권인지 PRD·결제 화면과 맞춘다. 2,900원은 확정한 상품 단위와 함께 쓰며 실제 매출로 표현하지 않는다 |

학생 간 비교와 풀이 공유가 미완성이라면 현재 차별성이 약하다는 점을 인정한다. 그때는 교안 근거를 확인하는 과정과 별도 AI 연결 설정 없이 쓰는 흐름까지만 실제로 보여 준다. 공동시험은 확정한 핵심 요구이지만, 확인 전까지는 미완료다. 채팅이나 공동 검수를 이미 제공한다고 말하지 않는다.

## 2. 증거를 모은 뒤 목차를 고정한다

1. **제출 기준 확인:** 운영진 안내에서 발표 시간, 시연 포함 여부, 장수, 파일 형식, 심사 기준, 제출 마감을 옮겨 적는다. 원칙 파일에는 이 대회의 확정 시간·장수·5인 분담이 없다.
2. **시연 하나 선정:** 직접 사용할 권한이 있는 PDF 하나와 같은 배포 주소를 사용한다. 교안 업로드 → 공통시험 생성 → 공유 링크로 두 학생 참여 → 답 제출·채점 → 같은 시험의 결과 비교 → 해설·학생 풀이 참고 순서로 확인한다. 미완료 구간은 시연 약속에서 빼고 요구사항에 남긴다.
3. **증거 기록:** 각 과정의 캡처, 사용한 교안 쪽, 생성 결과, 오류 여부를 남긴다. AI가 쓴 근거 쪽을 실제 PDF와 대조한다. 브라우저에만 저장된다면 다른 기기에서도 이어진다고 말하지 않는다.
4. **사업성 질문 점검:** 누가 왜 돈을 내는지, 생성 비용은 누가 내는지, 재사용 시 무엇이 다시 처리되는지 확인한다. 사용량이 없는 원가는 계산 가정으로 구분한다.
5. **장별 설계 확정:** 아래 순서에서 장 제목·화면 증거·발표자 문장·시간을 채운다. 제목만 읽어도 문제에서 결론까지 이어지는지 본다.
6. **제작과 동결:** 확인한 화면으로 제작하고 리허설한다. 배포가 바뀌면 같은 시연을 다시 확인한 뒤 캡처와 대본을 함께 갱신한다.

## 3. 발표 구성 제안

다음 8장은 제작 제안이며 대회 장수 규정이 아니다. 공식 시간이 짧으면 문제와 대안을 한 장으로 합친다. 시연 시간을 먼저 확보하고 기술 설명을 줄인다.

| 장 | 전달할 내용 | 화면에 둘 증거 |
| --- | --- | --- |
| 1 | passfinder는 같은 시험을 준비하는 학생들의 비교 학습을 돕는다 | 서비스 이름과 실제 시작 화면. 비교 기능 확인 전에는 구현 목표라고 표시 |
| 2 | 문제·시연·사업성을 차례로 설명한다 | 세 갈래 목차 |
| 3 | 교안을 읽은 뒤 연습문제와 답을 준비하는 일이 남는다 | 한 학생의 현재 준비 과정. 조사 전이면 상황 예시라고 표시 |
| 4 | 같은 문제를 풀고 서로의 결과를 확인한다 | 두 학생의 동일 시험 시연. 미완료이면 확인된 생성·조회 화면까지만 사용 |
| 5 | 공통 해설과 학생이 작성한 풀이를 구분해 참고한다 | 제출 후 실제 풀이 화면. AI 해설만 있다면 학생의 풀이처럼 소개하지 않음 |
| 6 | 생성 비용과 이용료를 함께 계산한다 | 확인된 과금 주체, 상품 단위, 비용 항목. 수요와 이익은 측정 전 조건 표시 |
| 7 | 같은 시험을 기준으로 비교해야 결과가 의미 있다 | 시험 버전·참여자 수·첫 응시·작성자 제외 기준. 검증 전에는 설계로 표시 |
| 8 | 시험 준비 시간을 줄이는지 실제 학생에게 확인한다 | 남길 결론, 다음 사용자 시험, 접속 주소, “질문 받겠습니다” |

질의응답용 부록에는 구조, AI·오픈소스 사용 내역, 비용 계산 조건, 문항 오류 처리와 자료 이용 권한을 둔다. 기술 이름을 나열하는 대신 어떤 사용자 행동을 지원하는지 설명한다.

## 4. 다섯 명의 담당 제안

실명과 역할은 팀이 정한다. 구현 담당자를 강제로 바꾸지 않고 발표 준비 역할을 나눈다.

| 역할 | 먼저 받을 것 | 맡을 결과물 | 완료 기준 |
| --- | --- | --- | --- |
| 발표 총괄 | 공식 제출 기준, 제출 PRD | 목차·대본·최종 파일 | PRD·발표·시연의 주장 일치 |
| 시연 담당 | 시연할 배포 주소·PDF | 시연 순서·캡처·실패 대비 | 다른 팀원이 같은 순서를 재현 |
| 문항 점검 | 생성된 문제와 원본 PDF | 정답·선택지·해설·근거 확인표 | 시연 문항의 오류나 범위 누락 설명 가능 |
| 사업성 담당 | 상품 정책·실제 AI 사용량 | 가격·비용 표와 질문 답변 | 계산 가정과 확인한 값을 구분 |
| 자료 제작 | 확정한 목차·캡처·대본 | 편집 가능한 슬라이드·PDF | 제목·본문·출처 가독성과 장별 대본 일치 |

마감 직전 새 기능을 발표에 추가하기보다, 이미 확인한 흐름을 모두가 같은 말로 설명하는 데 시간을 쓴다.

## 5. 제출 전 확인

- 원칙 파일의 G1~G13 중 해당하는 검사를 적용한다. 표지·마무리·로고 등 확정 요소를 보존한다.
- 본문은 한 장에 주장 하나와 증거 하나를 두고, 글꼴·색·여백을 통일한다. 본문 18pt 이상, 출처 12pt 이상으로 읽히게 한다.
- 같은 PDF로 생성한 문제의 정답·선택지·해설을 사람이 확인한다. 생성 성공을 정답 검증 완료로 바꾸지 않는다.
- 두 학생의 동일 시험 결과가 모이고, 다른 시험 결과는 섞이지 않는지 확인한다. 시험 작성자의 기록과 재응시를 순위에 넣는 기준을 설명한다.
- 시연은 새로 연 브라우저에서도 확인한다. 미리 생성한 결과를 보여 주면 그렇게 설명한다.
- 공개 캡처와 문서에 이메일·키·개인 MCP 주소가 남지 않게 한다.
- 발표자가 소리 내어 시간을 재고 공식 제한 안에 끝나는지 확인한다. 시간·장수 제한은 미확인 상태로 추정해 채우지 않는다.
- PPTX·PDF·대본의 내용이 일치하는지 확인하고, 공유 URL을 직접 연다.

현재 준비된 것은 원칙과 제작 흐름이다. 실제 슬라이드, 최종 배포 확인, 발표장 리허설은 이 문서 작성으로 완료된 것이 아니다.
