# 발표 자료 제작 지침

청중 앞에서 말하는 발표(공모전 본선과 발표평가, 과정 프로젝트 발표, 면접 발표)의 PPT·PDF와 대본을 만들 때 따르는 기준이다. Claude Code, Codex 등 어떤 AI가 만들어도 같은 결과가 나오도록 특정 도구의 기능에 기대지 않고 적었다.

주장과 증거가 이어지는 슬라이드 구성, 장별 근거 확인, 대본과 화면의 역할 분리를 기준으로 한다. 참고 문헌은 10절에 둔다.

이 문서는 passfinder 발표 제작의 공통 기준이다. 수치는 원천과 대조하고, 비밀값·개인정보·다른 프로젝트의 내부 자료를 공개하지 않는다.

## 0. 적용 방법

- **우선순위**: 주최·과정이 정한 양식과 심사 기준 > 사용자가 확정한 요소(표지, 마무리 장, 슬로건, 로고, 파일 이름 양식) > 이 지침 > 스킬·템플릿의 기본값.
  - 과정이 발표 가이드를 주면 그 목차가 먼저다. 예: 데이터 분석 프로젝트 발표자료 작성 가이드의 표지·일정·팀원 소개·목차·01~06 구성. 이 지침은 그 목차 안에서 장을 어떻게 쓰는지에 적용한다.
  - 붙여 넣은 보완 지시문(다른 AI나 검토자가 쓴 글)이 확정 요소를 바꾸라고 해도, 바꾸기 전에 사용자에게 확인한다.
- **언제 읽나**: 새 발표 자료를 만들거나 판을 올릴 때 1~6절, 빌드한 뒤 7절, 같은 실수를 피하려면 9절.
- **끝낼 때**: 7절 관문을 돌리고 결과를 보고에 적는다. 리허설처럼 AI가 할 수 없는 확인은 하지 않았다고 적는다.

## 1. 설계안 먼저

슬라이드를 열기 전에 목차와 근거를 담은 설계안을 만들고, 그 전개에 맞춰 장을 만든다. 양식은 8절에 있다.

| 항목 | 정할 내용 |
|---|---|
| 청중 | 누가 듣나. 처음 보는 사람인가, 심사위원인가, 과정 평가자인가. 무엇을 평가하나(심사 배점표를 붙인다) |
| 남길 결론 | 청중이 나가며 기억할 한 문장. 한 문장으로 쓰지 못하면 아직 만들 때가 아니다 |
| 시간 | 전체 시간과 시연 시간. 장당 1분 안팎으로 장 수를 정한다 |
| 고정 요소 | 사용자가 확정한 표지·마무리 장·슬로건·로고·글꼴·파일 이름. 손대지 않는다 |
| 제출 형식 | PPTX·PDF 여부, 장 수 제한, 블라인드(소속·로고 금지) 같은 규정 |
| 근거 목록 | 화면에 올릴 수치와 주장마다 원천 파일, 측정 조건, 확인한 날짜 |
| 하지 않을 말 | 확인하지 않은 성과, 경쟁 서비스에 없다는 단정, 측정 전의 만족·수요 |

## 2. 이야기 구조

### 2.1 청중이 따라올 순서

발표는 만든 사람이 아니라 처음 보는 청중을 중심으로 돈다. 기본 흐름은 어떤 문제를 풀려고 이 서비스를 내놓았고, 어떤 효과를 기대하며, 모델은 어떻게 도는지 말한 뒤 시연으로 넘어가는 것이다.

| 발표 종류 | 뼈대 |
|---|---|
| 서비스 발표 | 문제 → 지금 있는 대안과 부족한 점 → 해결 경험 → 시연 → 받쳐 주는 기술 → 확인한 것과 남은 것 → 다음 시험 |
| 연구·분석 발표 | 결론 먼저 → 데이터의 경계 → 검증 설계 → 결과 → 실패 조건 → 현장 적용 → 확인한 것과 못 한 것 |
| 과정 발표 | 과정 가이드 목차. 없으면 서비스 발표 뼈대에 과정 주제(예: 모델 서빙)를 받침으로 넣는다 |

- 표지 다음에는 목차(결론 지도를 겸해도 된다), 그다음 바로 문제 인식이 나온다. 기술 설명이나 팀 소개로 시작하지 않는다.
- 목차 장을 둔다. 목차의 갈래(예: 문제 · 서비스 · 모델 · 아키텍처 · 결론)를 각 장 왼쪽 위에 경로로 표시하고 지금 갈래만 강조한다. 목차 번호, 각 장의 소제목 번호, 실제 순서가 서로 같아야 한다.
- 제목만 이어 읽어도 이야기가 되어야 한다. 설계안의 제목 열을 이어 읽어 보고, 끊기는 곳이 있으면 슬라이드를 만들기 전에 구성을 고친다.

### 2.2 기능 나열 대신 한 사람의 여정

기능을 하나씩 설명하지 않고 사용자 한 명을 따라간다. 학생이 교안을 올리고, 문제를 만들고, 답과 해설을 확인하는 순서로 설명한다. 실제로 확인한 과정만 화면에 담는다.

### 2.3 시연은 일찍, 예고하고 보여 준다

- 청중이 7분 넘게 제품을 보지 못하는 구성은 피한다. 전체 발표가 짧으면 시연을 더 앞에 배치한다.
- 설명하는 장에서 "잠시 뒤 실제 서비스에서 직접 보여 드리겠습니다"로 시연을 예고한다. 그러면 시연이 앞에서 한 주장을 확인하는 자리가 된다.
- 시연 직전 장에서 볼 것을 세 가지 이내로 알려 준다. 예: 센터가 요청하고 회원이 확인해야 회차가 바뀌는지, PT 기록이 개인운동으로 이어지는지, 두 사람의 말이 다를 때 회차가 멈추는지.
- 발표에서 시연으로 넘어가는 흐름이 자연스러운지 설계안 단계에서 확인한다.

### 2.4 기술은 받침으로

과정 주제나 핵심 기술(모델 서빙 등)도 청중에게는 티 나지 않게 경험을 받쳐 주는 기본값으로 둔다. 제목은 사용자가 겪는 약속("원본을 먼저 전시하고, 모델 작업은 뒤에서 처리합니다")으로 쓰고, 기술은 본문과 대본에서 그 약속을 지키는 근거로 설명한다. 모델 수와 구조를 성과처럼 앞세우지 않는다.

다만 평가 기준이 기술 자체인 발표(과정 발표, 기술 심사)에서는 쓴 모델과 라이브러리를 빠짐없이 역할과 검증 상태로 소개한다.

### 2.5 대안을 먼저 인정한다

비슷한 서비스가 이미 있으면 먼저 말한다. "기능은 이미 있고, 저희가 시험하는 것은 조합입니다"처럼 차이를 좁고 정확하게 말해야 첫 질문에서 무너지지 않는다. 공개 자료에서 찾지 못했다고 다른 곳에는 없다고 말하지 않고, 조사한 곳과 날짜를 근거 줄에 둔다.

### 2.6 AI의 자리를 설계 원칙으로 말한다

AI가 하지 않는 일을 숨기지 말고 설계 원칙으로 보인다. 문항을 만드는 기능과 정답을 보증하는 기능을 구분한다. 실제 시험 점수나 학점을 보장하지 않는다.

### 2.7 한계는 주장 옆에, 남은 일은 한 장에

- 한계는 그 주장이 있는 장의 근거 줄에 붙인다. 작은 각주에 숨기지 않는다.
- 남은 검증은 결론 앞 한 장(확인한 것, 팀 시험, 아직)에 모은다. 본문 여러 장이 "아직 못 했다"로 읽히면 청중은 만든 것보다 없는 것을 기억한다.

### 2.8 마무리

- 마지막 장은 남길 결론 문장과 "질문 받겠습니다"가 있는 장이다. "감사합니다"만 있는 빈 장이나 부록으로 끝내지 않는다.
- 시연용 자료에는 향후 계획을 늘어놓지 않는다. 필요하면 QR 하나로 실제 주소를 걸고, 맞는 주소로 열리는지 확인한다.
- 부록은 마무리 장 뒤에 두고 질문받을 때만 연다.

## 3. 장 단위 규칙

### 3.1 제목은 결론, 본문은 증거 하나

- 제목은 항목 이름("서비스 구조", "결과")이 아니라 결론 문장이다. 제목에 주장 문장을 두고 본문을 그림 증거로 채운 슬라이드는 PowerPoint 기본 형식(항목 제목과 글머리표)보다 이해도가 높고 오해가 적었으며, 학습자가 느낀 인지 부담은 낮고 지연 회상은 좋았다(공학 전공 학생 110명 실험, Garner & Alley, 2013).
- 한 장에 메시지 하나, 증거 하나. 증거는 실제 화면 캡처, 실제 데이터 그림, 기본 차트, 단계 도식 중 하나다.
- 글만 있는 장을 만들지 않는다. 실제 화면, 과정 그림, 측정한 결과를 증거로 넣는다.
- 본문은 장당 40어절 안팎이다. 나머지 설명은 대본이 맡는다.
- 핵심 결과는 차트 위에 바로 적어 청중이 찾지 않게 한다.

### 3.2 청중의 말로

- 내부 코드(M3, D55, REQ-3), 파일 경로, 브랜치 이름, 점검 항목 번호, 차시명, HTTP 상태 코드를 화면에 쓰지 않는다. 만든 사람도 설명하기 어려운 아키텍처 도식은 "보호자 화면 → 서비스 서버 → AI 작업 서버"처럼 관계만 남긴다.
- 전문용어는 처음 나올 때 풀어 쓴다.
- 압축한 문구 대신 누가 무엇을 하는지 보이는 문장을 쓴다. 사용자가 확정한 슬로건은 글자 그대로 쓴다.

### 3.3 확인한 만큼만 말한다

- 수치마다 조건을 붙인다. 표본 수, 측정 환경(개인 PC, 팀 서버, 공개 서버), 기준일이다. 개인 PC 측정을 팀 서버 성능처럼 말하지 않는다.
- 확인한 범위보다 넓히지 않는다.
  - "탐지 수가 같다"를 "같은 구간을 찾았다"로 바꾸지 않는다.
  - 평가 그림 몇 장으로 확인하고 켰으면 "평가 통과"가 아니라 "사전 점검"이다.
  - 만족을 확인하지 않았으면 "더 나은 감상 방식"이 아니라 "새로운 감상 방식"이다.
  - "어떤 사진을 올려도", "실패하지 않는다" 대신 "모델 처리가 실패해도 저장된 원본을 먼저 전시하도록 설계했다"처럼 범위를 좁힌다.
- 이름이 뜻과 맞아야 한다. 시간 순서가 아니라 점수 순위로 고른 창을 "경보 직전 정상 창"이라고 부르지 않는다.
- 설계만 한 것과 시험한 것을 도식에서 나눈다. 예: 실선은 시험한 전환, 점선은 설계 단계.
- 근거 등급을 반복 표시로 쓴다. 모든 본문 장 아래 근거 줄 앞에 등급을 붙이면, 청중이 장마다 그 주장을 얼마나 믿어도 되는지 안다.

| 근거 등급 | 뜻 |
|---|---|
| 공개 서버 확인 | 누구나 여는 주소에서 직접 확인했다 |
| 팀 시험 | 팀 서버, 자동 시험, 합성 데이터로 확인했다 |
| 공개 자료 조사 | 다른 서비스의 공개 페이지 기준이다(기준일 표시) |
| 설계 가설 | 설계하며 세운 문제 상황이다. 조사로 확인하지 않았다 |
| 다음 검증 | 아직 측정 전이다 |

### 3.4 화면 캡처

- 지금 배포된 화면을 찍는다. 이전 판 화면이 섞이면 청중이 어느 쪽이 지금 제품인지 헷갈린다.
- 볼 곳을 크게 잘라 넣고, 한 장에 2~3개 이하로 둔다. 작은 전체 화면을 그대로 넣지 않는다.
- 캡처마다 무엇을 보여 주는지 설명을 한 줄 붙인다.
- 견본 데이터, 실제 모델 결과, 화면 효과, 미리 처리한 결과를 구분해 표기한다.
- 확인하지 못한 장면을 빈 상자나 예상 화면으로 채우지 않는다. "아직 공개 서버에서 확인하지 못함"으로 적고 시연 약속에서 뺀다.

## 4. 시각 체계

### 4.1 고정 요소를 지킨다

사용자가 확정한 표지, 마무리 장, 로고, 슬로건, 색은 다시 그리지 않는다. 고친 판을 만들 때는 고정 장을 그대로 두고 나머지 장을 고친 뒤, 고정 장이 원본과 같은지 대조한다(7절 G1).

### 4.2 체계는 시안으로 고른다

새 시각 체계가 필요하면 같은 핵심 장을 두세 방향으로 실제로 만들어 비교한다. 템플릿의 색만 입히지 말고 장의 정보 배치를 함께 검토한다.

### 4.3 색, 바탕, 글꼴

| 요소 | 기준 |
|---|---|
| 색 | 주색 하나와 강조색 하나. 강조색은 수치와 강조 단어에만 쓰고 본문이나 넓은 면을 채우지 않는다. 주제와 상관없는 색을 쓰지 않는다 |
| 바탕 | 본문 장은 밝은 바탕이 기본이다. 표지와 마무리는 어두워도 된다. 본문이 어두우면 밝은 발표장 프로젝터에서 회색 글자가 묻힐 수 있으니 밝은 예비판을 준비한다 |
| 글꼴 | 한 종류. 한글은 굵기가 다양한 고딕(예: Pretendard, SIL OFL 1.1 무료 글꼴)을 쓰고 PPTX에 글꼴을 넣어 저장한다. 발표장 PC에 그 글꼴이 없어도 같게 보인다 |
| 크기 | 표지 제목 40pt 이상, 장 제목 28~32pt, 본문 18pt 이상, 근거 줄·출처·쪽 번호 12pt 이상. 9~10pt 머리줄은 뒷줄에서 읽히지 않는다 |
| 정렬 | 모든 장이 같은 여백 격자를 쓴다. 표와 글상자를 꽉 채우지 않는다 |

### 4.4 쓰지 않는 장식

AI가 만든 티가 나는 장식이다. anthropic pptx 스킬의 금지 목록과 같다.

- 제목 밑 줄, 한쪽 세로 줄무늬, 장 가장자리 띠, 카드 한쪽 테두리
- 같은 배치의 반복(제목과 글머리표만 계속 이어지는 장)
- 내용과 상관없는 아이콘과 장식 그림
- 기본 차트를 도형으로 다시 그린 막대(편집과 수치 대조가 안 된다)

### 4.5 차트와 그림

- PowerPoint 기본 차트를 쓰고 내장 데이터를 남긴다. 차트 위에 지표 이름과 범위를 적는다.
- 주인공(우리 모델, 핵심 값)에만 강조색을 준다. 범례 대신 선 끝 라벨을 쓴다.
- 그림 속 글자가 본문 글자보다 작아지지 않게 다시 그린다.
- 값이 0이라 막대가 보이지 않는 차트는 숫자를 함께 적고, 옆 차트와 같이 읽히게 배치한다.

### 4.6 표지

- 프로젝트 이름, 한 문장 정의, 팀과 발표자를 둔다. 정의는 누가 무엇을 하면 무엇을 얻는지 보이는 한 줄이다.
- 날짜를 넣지 않는다. 발표일과 제출일이 달라 혼동된다.
- 머리줄과 쪽 번호를 두지 않는다. 쪽 번호는 목차부터 매긴다.
- 블라인드 대회는 소속, 학교, 로고를 넣지 않는다.
- 감성 문구는 한 줄만 남긴다.

## 5. 대본과 질의응답

### 5.1 대본

- 대본과 발표자 노트는 장별로 같은 글이다. 한쪽만 고치지 않는다.
- 말로 하는 문장이다. 짧게 끊고 "~습니다"로 쓴다.
- 화면의 글을 그대로 읽지 않는다. 그림과 말로 설명할 때 같은 문장을 화면에도 띄우면 오히려 덜 배운다(중복 원리, Mayer, 2009). 화면에는 주의를 이끄는 짧은 표지어만 두고 설명은 말로 한다.
- 장마다 꼭 남길 한 문장을 굵게 표시해, 발표자가 그 문장만은 놓치지 않게 한다.
- 한계를 말할 문장을 그 장의 대본에 넣는다. 예: "이건 저희가 설계하면서 세운 가설입니다. 아직 실제 가정을 조사해 확인하지는 않았습니다."

### 5.2 시간

- 장당 1분 안팎으로 잡고 시연 시간은 따로 둔다.
- 발표자가 소리 내어 읽으며 시간을 잰다. 정해진 시간보다 1~2분 짧게 끝나도록 맞춘다.
- 시간이 넘칠 때 줄일 문장과 줄이지 않을 문장(결론 지도, 마무리 문장)을 대본 끝에 적어 둔다.

### 5.3 말하지 않을 것

대본 끝에 목록으로 둔다. 확인하지 않은 품질, 경쟁 서비스에는 없다는 말, 측정 전의 만족과 재방문, 조건을 뺀 처리 시간이 대표적이다.

### 5.4 예상 질문

- 대본을 기준으로 만든다. 서비스와 문제에 관한 질문, 기술 질문(가장 중요한 설계 판단, 실패 처리, 처리 시간, 라이선스, 개인정보, 다시 한다면 바꿀 것)을 나눈다.
- 질문과 답을 표로 쓰고 답에도 한계를 붙인다. "검증을 통과했다" 대신 "검증을 수행했고, 그 결과에 따라 주장 범위를 줄였다"처럼 정확히 쓴다.
- 맨 위에 발표 전에 외울 숫자 카드(데이터 규모, 핵심 지표와 기준선, 표본)를 둔다.
- 답에 쓴 숫자도 원천과 대조한다. 슬라이드와 대본의 수치를 함께 고친다.

### 5.5 시연 대비

- 발표장 인터넷에서 시연 순서를 미리 한 번 해 본다.
- 시연이 막히면 같은 순서를 설명할 캡처 장을 둔다.
- 처리가 오래 걸리는 결과는 미리 처리한 작품으로 보여 주되, "미리 처리한 결과"라고 말한다.
- 로그인이 필요한 화면은 발표 전에 로그인해 둔다.
- 새 배포가 있었다면 발표 직전에 증거 장의 문장이 지금 상태와 맞는지 다시 본다.

## 6. 제작 방법

### 6.1 파일과 판

- 원본 PPTX는 보존하고 복사본을 고친다. 판 이름은 사용자가 정한 규칙(발표3, 발표4 …)을 따른다.
- 최종 파일 이름은 주최·과정 양식을 따른다.
- 최종 폴더에는 최종 PPTX·PDF·대본만 두고, 이전 판과 작업 자료는 작업 폴더로 옮긴다.
- 팀명, 팀원, 날짜는 원천 파일 하나(예: `submission_info.json`)에서 읽어 표지, 파일 이름, 문서 속성에 같이 쓴다.

### 6.2 PPTX를 만드는 방법

- **새로 만들 때**: 스크립트(pptxgenjs, python-pptx)로 생성한다. 화면 수치는 결과 파일에서 읽고, 핵심 값은 원천과 대조하는 assert를 둔다. 생성기는 정본을 바로 덮어쓰지 않고 작업 출력 폴더에 만든 뒤, 검사를 통과하면 옮긴다.
- **고칠 때**: 원본을 복사해 바꿀 장만 다시 그리는 빌드 스크립트를 쓴다.
- 모든 글자(run)에 `lang="ko-KR"`을 단다. 없으면 한글이 글자 단위로 쪼개지고 영문 이름 사이가 벌어진다.
- 차트와 표는 편집할 수 있게 둔다. 그림으로 바꾸지 않는다.
- 모든 장에 발표자 노트를 넣는다.
- PDF는 PowerPoint로 내보낸다. LibreOffice는 없는 글꼴을 폭이 다른 글꼴로 바꿔 렌더하므로 넘침 판정이 틀릴 수 있다.

### 6.3 스킬과 도구

| 도구 | 쓰는 곳 |
|---|---|
| academic-pptx 스킬 | 근거와 추론을 평가받는 발표의 구성(결론 제목, 증거 하나, 제목 이어 읽기, 시간 배분) |
| anthropic pptx 스킬 | PPTX 생성과 편집, 금지 장식 목록, 렌더 검사 절차 |
| frontend-slides 스킬 | 시각 체계 시안 비교. 결과물이 HTML이라 PPTX에는 디자인 참고로 쓴다 |
| 문구검사 도구 | 금지 문구와 내부 경로 검사(PPTX·PDF를 읽는다) |

설치한 스킬은 실제로 읽고 대조한 뒤에만 참고했다고 쓴다. 텍스트만 있는 장, 편집되지 않는 차트, 주제와 무관한 장식이 남았는지 확인한다.

## 7. 검사 관문

빌드 뒤 검사 스크립트 하나로 돌리고, 하나라도 실패하면 고친다. 기준 숫자는 설계안에 맞춰 바꾼다.

| 관문 | 검사 | 통과 기준 |
|:--:|---|---|
| G1 | 고정 장(표지, 마무리, 로고)이 원본과 같은가 | 도형·글자·그림 해시 같음, PDF 픽셀 차이 0 |
| G2 | 장 수와 순서 | 설계안과 같음 |
| G3 | 제목 이어 읽기 | 슬라이드 제목과 설계안 제목 열이 같음 |
| G4 | 근거 줄과 근거 등급 | 본문 장 전부에 있음 |
| G5 | 필수 문구와 조건 | 수치 옆 조건, 미검증 표시 누락 0 |
| G6 | 글자 크기 | 본문 18pt 이상, 근거 줄·쪽 번호 12pt 이상 |
| G7 | 본문 분량 | 장당 40어절 안팎 |
| G8 | 언어와 글꼴 | 모든 글자 `lang="ko-KR"`, 글꼴 하나 |
| G9 | 노트와 대본 | 장별 본문 일치 |
| G10 | 넘침과 쪽 밖 글자 | 0 |
| G11 | PPTX와 PDF | 장 수와 글자 같음 |
| G12 | 차트 수치와 원천 | 불일치 0 |
| G13 | 금지 문구 | 문구검사 오류 0. 제출물은 `--scope 공개` |

자동 검사 뒤에는 사람이 본다.

- PDF 전 장을 확대해 잘림, 겹침, 고아 줄을 눈으로 본다. 슬라이드 PDF는 고아줄검사가 글상자 사이에서 오탐을 내므로 자동 결과만 믿지 않는다.
- 처음 보는 사람이 되어 제목만 넘겨 본다. 무슨 서비스인지, 무엇을 확인했는지 알 수 있어야 한다.
- 바꾼 문구를 대본, 예상 질문, 보고서, README에서 검색해 같은 말로 맞춘다.
